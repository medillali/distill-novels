## 已复现的问题

基线使用应用自带 Python 3.12.14，运行未修改的上游脚本。输入全部是本次构造的短文本，无真实小说。详细输出位于本地 `work/audit-20261021/observations.json`；目录日期是测试准备时的会话日期。

### 1. 来源 ID 随导入集合改变

代码位置：`scripts/prepare_sources.py:84–86`。

操作：先导入仅有 b.txt 的目录；随后加入按名字排序更靠前的 a.txt，再处理同一目录。

实测：b.txt 的内容完全相同，ID 从 `book-01-eedacd7d` 变成 `book-02-eedacd7d`。

影响：长期卡片和图节点若引用旧 ID，新增小说后可能失去关联；仅将编号改成内容哈希仍不能处理同一书籍的内容修订。

设计要求：分别管理稳定作品 ID、内容版本哈希、旧 ID 别名；保留同一作品不同修订的证据定位。

### 2. 增量处理覆盖清单

代码位置：`scripts/prepare_sources.py:82,101`。

操作：向同一输出目录先处理 b.txt，再仅处理 a.txt。

实测：最新 manifest 的文件列表只有 `a.txt`。这证明旧来源从清单消失，不能推断旧文本文件也被删除。

影响：只补一本书时，后续工具无法通过最新清单发现旧书。

设计要求：明确区分新建与合并，先校验再写入；重复导入不增加重复资产，也不删除既有人工笔记。

### 3. EPUB 阅读顺序与 spine 不一致

代码位置：`scripts/prepare_sources.py:46–49`。

操作：构造包含 chapter2.xhtml、chapter10.xhtml 的最小 EPUB 测试包，并将 spine 设为 2 → 10。

实测：提取结果为 10 → 2，因为脚本按文件名字典排序。

影响：反转、伏笔、读者获知顺序可能被分析错误。

设计要求：按 OPF spine 读取；不完整 EPUB 明确警告，不能把文件名顺序当作已确认的叙事顺序。本样例验证提取器的排序行为，不代表已覆盖完整 EPUB 兼容性。
